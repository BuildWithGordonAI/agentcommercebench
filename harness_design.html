01 — Current Design

What exists today is a research benchmark. It proves the gap. It is not yet infrastructure.

02 — The Core Insight: P(Correct Behavior)

Flip the framing. Don't ask "does this look like an attack?" Ask:

What is P(this action is correct given this agent's behavioral profile and session history)?
Fraud score = 1 − P(correct). Proof of accomplishment = a signed log of this probability over the session. These are outputs of the same model — you keep everything that exists and add the probabilistic layer on top.

P(session correct) = ∏ P(aᵢ | context, agent_profile, a₁..ᵢ₋₁)

fraud_score(t) = 1 − P(aₜ | session_so_far, agent_profile)

Standards Strategy

03 — Open Source + Paper

Garak became a standard because it was open, comprehensive, and citable. Promptfoo became a standard because it integrated into CI/CD before alternatives existed. The pattern is always the same: open source creates the standard; managed service captures the business.

The open/closed line

Open source Apache 2.0
  • Attack taxonomy (A1–D2) and all probe code
  • Parameterized attack generator (N variants per scenario)
  • Proof certificate format spec (JSON schema + signing spec)
  • gordonguard CLI scanner
  • SDK — @gordonguard.watch decorator
  • AgentCommerceBench dataset (HuggingFace)
  • SGRF model weights (HuggingFace)
Managed service proprietary
  • Trusted signing authority for proof certificates
  • Per-agent behavioral baselines (trained on your sessions)
  • Continual learning across all connected agents
  • Cross-agent attack intelligence sharing
  • Dashboard, alerting, audit export
  • SLA + compliance reports (SOC 2, EU AI Act mapping)
  • Wallet/rail API integration

The certificate authority model. DigiCert didn't win by having the best encryption algorithm — SSL is open. They won by being the trusted signer that browsers accept. Gordon Guard publishes the certificate format openly. The business is being the signer that payment rails and insurers accept. Publishing the format doesn't give away the moat; it creates the moat by making everyone build against your spec.

CI/CD integration — the Promptfoo move

# .github/workflows/security.yml
- name: ACB security scan
  run: |
    pip install gordonguard
    gordonguard scan \
      --agent-url ${{ secrets.AGENT_URL }} \
      --attacks b3,a4,a7,d1 \
      --variants 20 \
      --fail-above 0.20    # fail CI if hit rate > 20% on any scenario
      --output acb-report.json

- name: Upload ACB report
  uses: actions/upload-artifact@v3
  with:
    name: acb-security-report
    path: acb-report.json

Developers add this to their CI pipeline before any agent reaches production. The coverage score becomes a deploy gate. This is how Promptfoo achieved adoption — it slotted into an existing workflow rather than requiring a new one.

Six pillars

Pillar 1
gordonguard CLI
Open source scanner. Works against any MCP agent. 15 scenarios × N variants. Hit-rate report. CI/CD gate. This is the distribution mechanism — everything else follows once the CLI is in use.
Pillar 2
Agent SDK
One decorator wraps production MCP calls. Async, <5ms. Streams signed event log. Works with LangChain, CrewAI, AutoGen, raw MCP. Bridges dev testing (CLI) to production monitoring (platform).
Pillar 3
Behavioral Likelihood Model
Per-agent profile. Starts from ACB prior. Fine-tunes as sessions accumulate. P(correct behavior) after each event. Rate-of-change signal distinguishes legitimate policy change from attack.
Pillar 4
Proof Layer
Signed attestation after every session. Verifiable by any third party. Format is open; signing authority is proprietary. Agent owner presents to insurer, auditor, counterparty, or payment rail.
Pillar 5
Continual Learner
Attack on agent A propagates to all agents. Novel attack → auto-generate variants → test connected agents. Human labels → active learning loop → fine-tune shared model. Data flywheel activates here.
Pillar 6
Wallet/Rail API
Payment rails query proof before authorizing agent transactions. This is the PCI-DSS moment: once one rail requires Gordon Guard proof, adoption becomes mandatory for any agent on that rail.

Each persona has a different entry point, a different first value moment, and a different relationship to the business. They need to be onboarded differently — and they unlock each other.

  • 2pip install gordonguard
  • 3gordonguard scan --agent-url localhost:8080 — gets coverage report in under 5 minutes

  • 5Adds to CI/CD pipeline as a deploy gate
  • 6Shows coverage badge + ACB report to their company's security team
First value: coverage report in <5 min
Free tier — open source CLI. Paid only if their company registers the production agent. Builders are distribution, not revenue.
🏢
Agent Owner
Company deploying agents that make real payments in production
  • 1Their builder recommends it, or compliance/security team finds the ACB paper
  • 2Registers at gordonguard.ai — gets agent_id + API key
  • 3Adds @watch(agent_id=...) to production agent — one line
  • 4Dashboard shows live sessions, per-event risk scores, alerts
  • 5Proof certificates generated automatically each session
  • 6Presents certificates to auditor, insurer, or counterparty
  • 7Behavioral model fine-tunes as their agent's sessions accumulate
First value: first proof certificate — proof they were in-policy
Per-agent seat: $X/month per registered agent. Per-certificate fee for high-value transactions. Enterprise: compliance report + SLA.
🔗
Wallet / Rail Owner
Payment infrastructure: Stripe, Coinbase, AWS MCP, payment processors
  • 1Gordon approaches as infrastructure partner — after paper and agent owner traction
  • 2Integrates POST /v1/proof/{session_id} API into authorization flow
  • 3Optionally: requires Gordon Guard proof for agents transacting above $X threshold

  • 6Documents Gordon Guard in their developer security requirements
First value: fraud reduction on their platform without changing their core infra
Revenue share on fraud prevented, or per-verification API call, or enterprise partnership contract. This is the PCI-DSS moment: when one rail requires the certificate, every agent on that rail must onboard.

The four moats

Moat 1
Data flywheel
More agents → richer behavioral baselines → better detection for all. Attack seen on agent A propagates to all connected agents. The system gets structurally better with scale — a static scanner cannot.
Moat 2
Taxonomy standard
ACB attack codes (A1–D2) become the industry vocabulary. Other vendors map to them. Compliance docs reference them. The company that names the attacks owns the conversation.
Moat 3
Certificate authority
Once a payment rail or insurer accepts "Gordon Guard Proof," agent owners cannot switch without re-establishing that trust. Compliance integrations are structural — they don't get un-integrated.
Moat 4
Per-agent baseline
Switching means losing the behavioral baseline trained on your agent's production sessions. That trained profile is owned by the agent owner — but only exists inside Gordon Guard. High switching cost by design.
